# Воспроизводимые проверки

Тесты проверяют приложение без оплаты модельных запросов и без пользовательских шаблонов. Production не содержит переключателя на тестовые ответы: код replay находится только в `test_support/` и запускается тестами.

## Запуск

Нужны Python 3.12+, LibreOffice Impress и включённые в репозиторий шрифты. На Linux установите `libreoffice-impress`; на macOS приложение использует установленный LibreOffice. Отсутствие нативного renderer считается ошибкой, а не причиной пропустить сквозную проверку.

```bash
python -m pip install -r requirements.lock -r requirements-dev.txt -r requirements-e2e.txt
python -m playwright install chromium
# В Linux CI для установки системных библиотек:
# python -m playwright install --with-deps chromium

ruff format --check studio tests scripts test_support e2e audit_e2e
ruff check studio tests scripts test_support e2e audit_e2e
node scripts/ui_phase_labels_test.cjs
python -m pytest -q
python -m pytest -q e2e --junitxml=test-results/browser.xml
```

Обычный `pytest` запускает `tests/` и `audit_e2e/tests/`; Chromium проверяется отдельной явной командой. В GitHub Actions четыре jobs (`lint`, `test`, `browser`, `hermetic-evaluation`) входят в один workflow. Последний запускает браузерные сценарии из `audit_e2e/e2e/` и основной replay-корпус в Linux с `--network none`. Browser job не имеет `continue-on-error` и ограничен 15 минутами. Playwright закреплён отдельно в `requirements-e2e.txt`, чтобы браузер не становился зависимостью приложения.

Быстрая проверка изменённого контура:

```bash
python -m pytest -q tests/test_model_replay.py tests/test_diverse_inputs.py
python -m pytest -q e2e
```

## Что воспроизводится

`tests/fixtures/model_responses/*.json` содержит заранее заданные **синтетические** HTTP-ответы. Это не запись реального провайдера и не оценка качества Qwen. Успешные ответы вручную составлены для открытого синтетического текста из `test_support/inputs.py`; ответы критиков без замечаний проверяют передачу результатов проверки, а не эстетическое качество слайдов.

Replay работает на границе HTTP: настоящий `ModelGateway` строит запросы, разбирает ответы, применяет повторы и валидацию. Сценарии `e2e/test_browser_flows.py` проходят через настоящий FastAPI, фоновые процессы, DeepPresenter, аудит и LibreOffice; маршруты приложения в них не подменяются. Два отдельных сценария `e2e/test_workflow_ui.py` проверяют только DOM и HTTP-контракты редактора брифа и выбора исправлений на заданных ответах API. Реальная серверная логика этих операций проверяется отдельно в `tests/test_workflow_api.py`, `tests/test_store_workflows.py` и `tests/test_selected_repair.py`.

Ключ ответа включает хеш полного system prompt, пользовательский payload, JSON-схему, модель и параметры генерации. Для каждого одинакового запроса есть конечная очередь ответов. Изменённый, лишний или повторный запрос после исчерпания очереди немедленно отклоняется; неиспользованные ответы также проваливают проверку. Автоматической записи, обновления эталонов или обращения к настоящему провайдеру нет. В `replay-report.json` сохраняются стадия, хеш и контракт неожиданного запроса.

По умолчанию изображения сравниваются по байтам PNG и размерам (`pixels`). В браузерных кассетах явно выбран режим `dimensions`: отрисовка LibreOffice отличается между платформами, поэтому сравниваются количество, порядок и размеры изображений, а текст и остальные поля остаются точными. Такой replay **не обнаруживает замену пикселей при сохранении размеров** и не является визуальным snapshot-тестом. Геометрия и содержание экспорта проверяются отдельно.

Набор ответов охватывает успешный полный путь, отказ авторизации на анализе и генерации, HTTP 429 с повтором, повреждённый JSON, `finish_reason=length`, исправление неверной схемы и исчерпание двух попыток. Проверяется, что кэш получает только валидированный ответ.

## Сквозные сценарии

- Загрузка PPTX, анализ, генерация трёх вариантов, отдельная проверка изображений, скачивание ZIP и чтение итоговых PPTX; сохранение фактов и отсутствие старого текста шаблона.
- Открытие истории после перезагрузки, повторный анализ через кэш без модельных запросов, блокировка генерации после изменения текста.
- POTX 4:3 с английским текстом и таблицей; тёмный шаблон с колонками, русским текстом и загруженной иллюстрацией.
- Отказ провайдера на анализе/генерации: краткий статус в интерфейсе, техническая причина в журнале, отсутствие опубликованного результата. При отказе предварительного анализа подготовка получает ошибку зависимого задания и ссылку на её техническую причину в журнале; кассета фиксирует один терминальный HTTP 401 без скрытого повтора или кеширования отказа.
- Блокировка текстовой prompt injection и восстановление формы после сброса.

Каждый тест запускает свой сервер на свободном loopback-порту, использует новую временную папку данных и завершает собственную группу процессов. Настройки создаются явно, `.env`/`.env.team` не читаются; переменные `STUDIO_*`, `LLM_*`, `OPENROUTER_*` удаляются из окружения дочернего процесса. Тестовый ключ пустой, HTTP-провайдер слушает только loopback; внешние запросы браузера запрещены. Рабочая папка `data/v2/` и сервер на 8765 не используются.

## Разнообразие входов

Генератор создаёт PPTX/POTX из параметров, без готовых пользовательских файлов: форматы 16:9 и 4:3, светлый и тёмный фон, одна/две/три текстовые колонки, разные поля. Seed фиксирует вход и позволяет повторить ошибку; случайность не делает CI нестабильным.

Серверная матрица сочетает русский, английский и смешанный текст, таблицы и числовые факты. Проверяются полное покрытие источников, отсутствие ошибок геометрического аудита и старого текста. Отдельный тест переименовывает те же байты шаблона: геометрия, палитра и доступные макеты должны совпасть. Повреждённый архив отклоняется до анализа. Браузер добавляет проверку загрузки изображения и настоящего экспорта.

Это конечная регрессионная матрица, а не доказательство поддержки любого PowerPoint. Для новой ошибки сначала выделите независимый признак (например, длинный текст или нестандартный контейнер), добавьте синтетический вход и проверку нарушенного свойства. Не добавляйте в production ветвления по имени шаблона, его хешу или seed.

## Как разбирать сбои и менять эталоны

1. В GitHub откройте упавший job и скачайте `browser-evidence`. Локально артефакты лежат в `test-results/browser/`: скриншот, trace, серверный лог и отчёт replay. Просмотр: `python -m playwright show-trace path/to/trace.zip`.
2. При несовпадении replay сравните контракт из отчёта с `request` нужной кассеты. Изменение промпта, схемы или входа требует осмысленного пересмотра ответа; нельзя просто ослабить сравнение до имени стадии.
3. Если изменение намеренное, вручную обновите только соответствующие запросы/ответы в JSON. Системный prompt хранится хешем; новый хеш можно получить из отчёта несовпадения. Для полной пересборки используйте синтетический вход и локальный HTTP transport с явно заданными ответами, затем проверьте весь diff. Не копируйте закрытые материалы и реальные ключи.
4. Сохраните `schema_version`, `provenance` и явную политику изображений; проверьте источники чисел, ожидаемые повторы и причину успешного/неуспешного ответа. Выполните gateway-тесты и браузерный набор перед коммитом.

Реальный модельный прогон — отдельная проверка: он нужен для оценки качества, разнообразия оформления и поведения актуальной модели. Успешный replay его не заменяет. Не включайте платные запросы в CI автоматически.

## Архитектура и новые сценарии

`tests/test_architecture.py` рекурсивно проверяет импорты, циклы, границы HTTP и отсутствие импортов FastAPI/Starlette в предметных пакетах. Зависимости кеша проверяются на существование; перенос модуля меняет версию.

`tests/test_brief.py` и `tests/test_workflow_api.py` проверяют точное утверждение плана и текста, сброс утверждения после редактирования и запрет генерации до согласия. `tests/test_review_snapshot.py` и `tests/test_selected_repair.py` проверяют неизменяемый аудит, реальную композицию/экспорт исправленной версии, сохранность исходного результата и неизменённых вариантов.

`tests/test_template_resources.py` и `tests/test_resource_render.py` используют синтетические ресурсы: происхождение, отделимые рамки, редактируемые объекты PPTX и согласованную геометрию экспорта. Это не демонстрация классификации ресурсов актуальной VLM на неизвестных шаблонах.

Последняя проверка доработки: [28.09.2026](docs/VALIDATION_2026-09-28.md).

## Внешние шаблоны и проверка браузером

`scripts/check_external_templates.py` принимает настоящий PPTX/POTX и по умолчанию
запускает изолированный extractive сервер без ключей и платных вызовов. Проверяются
повторный анализ и кеш, подготовка, три варианта, нативный экспорт, ZIP и история.
Для короткого брифа дополнительно проверяются запрет запуска до утверждения и
точные хеши утверждённого черновика. Число слайдов задаётся явно:

```bash
python scripts/check_external_templates.py /path/template.potx --slides 5
python scripts/check_external_templates.py /path/template.potx \
  --input-mode brief --slides 2 --content /path/brief.md
python scripts/check_external_templates.py /path/template.pptx \
  --content /path/material.md --image /path/dashboard.png --image-presentation device
STUDIO_E2E_TEMPLATE=/path/template.potx python -m pytest -q e2e/test_external_template_ui.py
```

Последняя команда проходит настоящий DOM, HTTP, worker и экспорт для готового
материала и редактируемого брифа; без `STUDIO_E2E_TEMPLATE` эти два теста пропускаются.
Сторонние шаблоны и артефакты сохраняются только в игнорируемом `test-results/`.
Отсутствие рамки устройства должно отображаться как обычная вставка с пояснением.

Подключение к серверу с моделью требует `--url` и явного `--allow-model-calls`.
Этот флаг **не ограничивает расходы**: бюджет и контроль использования провайдера
настраиваются отдельно перед запуском. Успешный HTTP-прогон не заменяет просмотр
изображений: проверяйте единицы измерения, различимость вариантов и читаемость.
Корпус, найденные дефекты и фактические результаты: [отчёт о внешних шаблонах](docs/EXTERNAL_TEMPLATE_VALIDATION_2026-09-28.md).

## Независимая оценка презентаций

`python -m audit_e2e` запускает фиксированный корпус в `replay` или
ограниченном `live` режиме, сохраняет конечные файлы и независимые реестры фактов.
Подкоманды `judge`, `compare` и `calibrate` работают с сохранёнными результатами.
Команды, статусы, ограничения и порядок обновления кассет описаны в
[руководстве E2E-оценки](audit_e2e/README.md). Успех replay подтверждает контракт
исполнения; смысловая оценка актуальной модели требует отдельной калибровки.
