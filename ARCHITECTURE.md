# Архитектура

## Два этапа

```text
index-examples → reference profiles (independent styles)

PPTX + text + audience + instructions
  → ZIP/XML validation
  → template tokens + native source patterns + safe assets
  → sanitized source artwork → LibreOffice → cached template layers for HTML
  → facts + tables + constraints
  → text/geometry LLM classification of template patterns (not VLM)
  → optional labelled brief proposals + validated content plans
  → deterministic composition policies + geometry feasibility check
  → PreparedPackage + DESIGN.md + hashes
  → READY

POST /api/generate (timer starts here)
  → immutable-package validation
  → dedicated worker process
  → reuse frozen content plans (legacy packages: bounded planning)
  → DeepPresenter Design: compose_slides → inspect_variants → finalize (or explicit native engine)
  → compose + repair + cross-variant geometry diversity check
  → three bounded parallel render branches
  → deterministic audit + one repair pass
  → native PPTX / live HTML / PDF / previews
  → optional text-model critic
  → manifest + ZIP
  → COMPLETED / NEEDS_REVIEW, all within 300 seconds
```

Подготовка не экспортирует скрытые готовые колоды. Смысловой разбор, расширение brief, планирование и проверка допустимости композиций происходят до таймера; план фиксируется в PreparedPackage. Сборка итоговых сцен, повторный аудит, экспорт всех трёх колод и critic выполняются после старта таймера. Второе generation job отклоняется с 409, если первое ещё работает.

Три примера организаторов получают независимые технические профили, цветовые отчёты и семантические классификации внутри одного атомарно публикуемого поколения библиотеки. Отдельный процесс пересобирает всё поколение при изменении кода, промптов, конфигурации, модели, шрифтов или исходников. Пользовательские задания только читают готовое поколение. Его абстрактные роль/плотность/число областей помогают планировщику; стили не смешиваются. Подробнее: [REFERENCE_LIBRARY.md](REFERENCE_LIBRARY.md). Пользовательский шаблон разбирается отдельно: модель получает геометрию и короткие очищенные текстовые образцы, возвращает только enum-роли и плотность для существующих pattern IDs. Роли влияют на выбор подходящего исходного макета после приоритета вместимости. Рендер исходных макетов локальный. Подготовительный анализ не называется VLM: отдельный opt-in visual critic проверяет PNG уже сгенерированных презентаций.

Parser v5 сохраняет признаки списков и emphasis, извлекает до шести body-зон, титульные, парные heading/body и номерные зоны. Границы заголовка учитывают фактическую плашку. Композитор создаёт отдельные редактируемые абзацы/native bullets и сохраняет графику выбранного примера. Аудит дополнительно проверяет вмещение в исходный контейнер. Пакеты до v5 требуют повторного анализа; старые файлы сохраняются.

После PPTX→LibreOffice→PNG запускается visual critic, если оператор разрешил передачу изображений (`STUDIO_VLM_ENABLED=true`). До 4 изображений в одном запросе, не более 100 секунд и остатка общего 300-секундного дедлайна с резервом на упаковку. HTTP 400/413 уменьшает пакет вплоть до одного изображения внутри прежнего бюджета; 401 не повторяется. Проверка всех страниц обязательна: номера сверяются, хеши PNG фиксируются. Неполный/отключённый critic или его замечания дают API-результату needs_review. Визуальные замечания не исполняются как команды и не считаются автоматическим исправлением. Контракт проверен mocks, живые результаты после разрешения пользователя зафиксированы в TEST_REPORT.md. Отсутствие замечаний модели не доказывает отсутствие дефектов.

## Дедлайн

`created_at` фиксируется при принятии generation request. `deadline_at=created_at+300`. На POSIX supervisor завершает выделенную группу процессов worker вместе с дочерними LibreOffice; ветки рендера — три потока. Один вызов LibreOffice ограничен 45 секундами. Гарантия завершения дерева процессов на Windows требует отдельного Job Object и пока не проверена. Поздний результат не может заменить `timed_out` на `completed`.

У подготовки нет конкурсного суммарного лимита: отдельный анализатор макетов и author ограничены 180 секундами на запрос, planner вместе с одним repair — 360 секундами. Новые пакеты при генерации не повторяют author/planner. Для старых пакетов сохранён путь 45/120 секунд с резервом на экспорт. Если JSON невалиден или запрос не удался, включается явно отмеченный экстрактивный fallback, не считающийся успешной проверкой модели. Текстовый critic ограничен 25 секундами внутри общего дедлайна. Замечания привязаны к variant/slide, точному title_quote и fact_ids; непривязанный результат не считается завершённой проверкой. Один повтор временной сетевой ошибки остаётся внутри исходного timeout запроса. Экспорты выполняются в трёх потоках. PDFium-вызовы сериализованы отдельным lock.

Дубли раскладок модели больше не являются ошибкой плана. Код назначает политики композиций, сохраняя заголовки, ссылки на факты, таблицы и порядок. После repair сравниваются fingerprints геометрии содержательных объектов (без заголовков, имён файлов, layout labels и notes). Совпадения устраняются перестроением внутри исходных зон с изменением ширины на 16–28% и положения. Кандидат не должен добавлять геометрические ошибки. Если безопасного варианта нет, контент всё равно экспортируется с `needs_review` и `composition_diversity.verified=false`. Абсолютное обещание трёх визуально удачных композиций для любого произвольного шаблона не даётся.

## DeepPresenter runtime

В `studio/_vendor/deeppresenter` сохранён минимальный MIT-код из commit `2e68c095a86bdbb91635dc4d91dad4662aba163c`. Импорты изолированы namespace, upstream Docker/MCP env заменён ограниченным `CompositionEnvironment`. GatewayBridge переводит один строго проверенный JSON-action в тип сообщения tool call. `Agent.action/execute` и `Design.loop` выполняются реально, но не имеют upstream shell, Research, browser, filesystem tools или HTML-кода модели. Системные инструкции — `prompts/deeppresenter.md` и `config/deeppresenter.yaml`.

Завершение допускается после выбора полного набора композиций и проверки текущей ревизии. Кандидат применяется атомарно; ухудшающие геометрию назначения восстанавливаются до проверенного baseline с явным repair report. token:auto — ограниченный fallback по токенам шаблона, не новый стиль. Модель выбирает композиции; последующие inspect → finalize выполняются детерминированно через проверяемые инструменты. Текст и связи с фактами неизменны. Итоговая геометрия после diversity снова проходит аудит перед экспортом. До 6 ходов, весь Design до 90 секунд; запрос получает остаток бюджета стадии с резервом до 5 секунд на локальные проверки. Резерв 150 секунд на экспорт/финальные проверки, всё внутри общего лимита 300 секунд. Ошибка стадии не запускает неявный fallback. Native-движок выбирается оператором явно. Старые PreparedPackage без prepared_plans поддерживаются прежней ограниченной стадией планирования.

UI не показывает текущий таймер или проценты: анализ и генерация сопровождаются CSS-анимацией сборки слайдов и реальным текстом фазы. Анимация отключается при prefers-reduced-motion. Длительности анализа и генерации показываются только в готовом результате; analysis_seconds копируется из соответствующего immutable package, elapsed_seconds берётся из завершённого задания. Старые результаты получают длительность анализа по собственному package_id. При ошибке лоадер скрывается, сообщение остаётся под кнопкой, повторная генерация не требует нового анализа.

## Состояния

Подготовка: `accepted → running → ready | failed`.

Генерация: `accepted → running → completed | needs_review | failed | timed_out | cancelled`.

`needs_review` означает, что файлы доступны, но есть обязательные проверки с ошибкой. Это не зелёный успех. Неполные результаты после тайм-аута не выдаются через download API. После перезапуска незавершённые задания помечаются прерванными.

## Данные и версии

У каждой подготовки и генерации свой UUID-каталог. В `PreparedPackage` — SHA-256 исходного PPTX, текста, ограничений, версия анализатора и OpenDesign commit. Перед генерацией проверяется неизменность package и PPTX. Изменение пользовательских инструкций создаёт новый пакет, который ссылается на предыдущий; старые результаты сохраняются.

API не выдаёт `package.json` или исходный PPTX. Для скачивания разрешён конечный список имён файлов. База SQLite и загрузки находятся только в `data/`; эта директория не попадает в Git.

## OpenDesign

Используются материалы официального репозитория `nexu-io/open-design`, commit указан в `vendor/opendesign/PROVENANCE.json`. Это интеграция инструкций дизайна и формата design package, а не скрытый вызов закрытой модели через OpenDesign. Craft дополняет template contract; правила исходного PPTX имеют приоритет. Пакет допускает дальнейшее подключение daemon/skill workflow, но в текущем runtime этого нет.

Craft сформулирован императивно и включён в system prompt планировщика, то есть
это инструкции, а не пассивная справка. Отдельных кодовых gates соблюдения craft
нет. Влияние на конкретные визуальные дефекты не доказано; размеры, координаты
и цвета определяются нашим компоновщиком. Границы интеграции и рекомендация по
возможной миграции описаны в [ENGINE_BOUNDARIES.md](ENGINE_BOUNDARIES.md).

## Рендеринг

Сохраняются source master/layout/theme, фоновые изображения и безопасная нативная графика выбранного примера. Удаляется старый текст, а не весь shape tree. Для ordinary slides не переносятся непроверенные фотографии, таблицы и charts. Новое содержимое располагается в исходных title/body zones; при необходимости единая body-зона делится на колонки. Выбор учитывает вместимость. Сложные picture-driven макеты не используются как пустые фоторамки.

PPTX повторно открывается и проверяется на редактируемость и отсутствие external relationships. Затем LibreOffice отрисовывает именно этот PPTX в PDF; PNG получаются из PDF. HTML содержит подготовленный растровый фон плюс живое содержимое сцены, а PPTX — нативную графику, не этот растр. Цвет текста оценивается отдельно для каждой исходной зоны. Кэш слоёв защищён SHA-256 в PreparedPackage. При отсутствии LibreOffice используется явно отмеченный резервный PDF сцены и статус needs_review; дизайнерская/VLM-оценка не имитируется.

Планировщик получает required_outline, если исходные «Слайд N» согласуются с заданным числом слайдов. При семантической ошибке предусмотрен один repair в бюджете текущей стадии. Совпадение композиций не запускает repair. Причина от локального валидатора записывается в отчёт. Ошибки провайдера не отражаются целиком, чтобы не раскрыть payload или ключи. Critic получает обязательную JSON-схему findings.

## Подключённый inference и OCR-расширение

В локальном API-режиме используется NeuralDeep и документированный alias `qwen3.8-27b-noreason`. Провайдерские настройки и ключ остаются на сервере. Structured output ограничивает число слайдов и допустимые fact/table IDs уже в JSON-схеме; локальная семантическая валидация остаётся обязательной. В manifest пишутся usage и длительности вызовов, но не ключи и не reasoning-тексты. Сбой модельной стадии даёт `needs_review`, а не успешный статус только по геометрии.

OCR-транспорт вынесен в `studio/ocr.py`, не активирован в pipeline. Распознавание исходных материалов должно выполняться до фиксации PreparedPackage; проверка выходных слайдов — внутри общего дедлайна. У загрузки и получения результата разные методы, чтобы не повторять списание квоты при сетевой неопределённости. Условия включения, в том числе проверка допустимости OCR-модели, описаны в OCR.md.
# Семантический конвейер v2

Актуальное описание центрального процесса: [SEMANTIC_PIPELINE_V2.md](SEMANTIC_PIPELINE_V2.md).
Структура документа и паспорта назначения макетов формируются до планирования. Обложка и разделители резервируются в общем лимите. Выбор композиции, аудит и исправления используют общий контракт из `studio/contracts.py`. Финальная VL-проверка сравнивает реальный PPTX с исходным референсом; один ограниченный цикл исправления проверяется повторным рендером. Старые подготовленные пакеты требуют нового анализа, результаты не удаляются.
