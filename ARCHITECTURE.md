# Архитектура VK Forma

Композиции вариантов, повторное использование таблиц и проверка готовых PPTX описаны в [отдельном разборе](docs/structural-composition.md).

Описание backend после рефакторинга, обновлено 29.09.2026. Установка — [TEAM_SETUP.md](TEAM_SETUP.md), правила исправления — [REPAIR_ROUTING.md](REPAIR_ROUTING.md), воспроизводимые проверки — [TESTING.md](TESTING.md). [Исторические отчёты](docs/history/README.md) описывают состояние на момент проверки.


## Размещение кода

```text
studio/
  app.py, api/                  HTTP и сборка приложения
  presentation_service.py      Пользовательские сценарии и правила запуска
  pipeline.py                  Входные функции worker
  preparation/, generation/    Последовательность этапов
  contents/                    Разбор, бриф, редактура и планирование содержания
  templates/                   Геометрия, шрифты, палитра, анализ и каталог ресурсов
  composition/                 Сцены, нативные объекты, PPTX/PDF/HTML, ZIP и evidence
  checks/                      Аудит, качество, ограниченные исправления
  providers/                   Gateway, транспорт и адаптеры внешних компонентов
  jobs/                        SQLite, runtime и worker-процессы
  models.py, config.py          Общие типы и настройки
```

Внутренние импорты указывают на конкретные модули. Пустые `__init__.py` только объявляют пакеты; старых реэкспортов из корня нет. `PreparedPackage.control` хранит типизированные решения выполнения, `analysis` — диагностику. При публикации отчёта HTTP прежние поля анализа восстанавливаются из control, поэтому контракт интерфейса сохраняется.

## Границы приложения

```text
HTTP → api/ → PresentationService → JobRuntime → worker
                    ↓                           ↓
                Store (SQLite)               pipeline
                                                ↓
                                  preparation/ или generation/
```

`app.py` собирает FastAPI, зависимости, middleware, маршруты и lifespan. Маршруты разбирают HTTP-запрос, вызывают прикладной сценарий и формируют ответ; ошибки приложения преобразуются в HTTP на этой границе. `PresentationService` работает с обычными Python-значениями, `Settings`, `Store` и `JobRuntime`.

`JobRuntime` владеет фоновыми задачами, двумя слотами подготовки, ожиданием предварительного анализа, автозапуском и группами процессов. Сервис передаёт runtime уведомление о завершённой подготовке и callback запуска. Runtime не импортирует HTTP или прикладной сервис. Резервация одной генерации, отмена и запрет позднего изменения отменённого задания остаются транзакциями конкретного SQLite `Store`.

Пакеты подготовки и генерации не импортируют API, PresentationService или runtime. Рекурсивный архитектурный тест проверяет циклы, включая локальные импорты, и направление зависимостей. Общие схемы находятся ниже их потребителей. Новые интерфейсы хранилища, контейнер внедрения зависимостей и универсальный движок pipeline не требуются текущему приложению.

## Подготовка и генерация

```text
PPTX/POTX + текст + таблицы + изображения + ограничения
  → проверка ZIP/XML и входных данных
  → разбор шрифтов, цветов, исходных зон и графики
  → проверенный кэш конкретного шаблона либо его анализ
  → смысловой план с привязкой утверждений к источникам
  → детерминированная композиция и проверка вместимости
  → адресные исправления по типу и месту дефекта
  → независимая проверка смысла
  → PreparedPackage + DESIGN.md + контрольные суммы
  → ready

POST /api/generate
  → проверка версии и целостности PreparedPackage
  → отдельный worker process
  → подготовленные планы + ограниченный DeepPresenter Design
  → compose / repair / проверка разнообразия
  → выбранные пользователем один или три варианта PPTX / HTML / PDF / PNG
  → аудит фактических PPTX и разрешённая визуальная проверка
  → проверка допустимости публикации
  → manifest + ZIP → completed / needs_review
  → при блокирующей ошибке: failed, диагностика вместо публикации
```

Примеры организаторов регистрируются как исходные файлы. Предварительный анализ библиотеки запускается явно командой CLI; загрузка пользовательского шаблона запускает его анализ сразу. Обе точки входа используют `preparation/template.py` и общий проверяемый кеш. Нет правил, привязанных к именам конкретных шаблонов. Семантические ответы и технический профиль кэшируются по входу, конфигурации и зависимостям; принятые ответы повторно валидируются. Повтор задания может заново выполнить локальный разбор и рендер: полное возобновление всех стадий не реализовано.

Редактор сохраняет исходный документ и происхождение утверждений. При включённом сокращении он выбирает главные мысли, а исключённые факты передаёт независимой проверке смысла. Табличные данные остаются связанными с источниками; допустимые проекции колонок должны вместе сохранять все исходные колонки. Сокращение не даёт права менять числа или удалять существенные оговорки.

Проверка анализа использует ту же окончательную сцену, что экспорт, включая перевод данных в диаграммы. Адресные замены сохраняют число и порядок слайдов; принятые соседние слайды не переписываются. Геометрия сначала исправляется детерминированно. Ограничение числа повторов не считается доказательством качества.

## Контракты этапов

`pipeline.py` — входные функции и проверка целостности пакета. Подготовкой управляет `preparation/orchestrator.py`, генерацией — `generation/flow.py`. Предварительный анализ без текста и полная подготовка используют общий путь обработки шаблона. `TemplateAnalysisResult` явно передаёт профиль, анализ и хеши слоёв; клиент модели создаётся и закрывается один раз на операцию. Результаты планирования, экспорта, проверок и исправлений имеют явные схемы в `generation/results.py`; JSON формируется на границах хранения и внешних компонентов. Контракты, владельцы функций и оставшиеся ограничения описаны в [STAGE_CONTRACTS.md](STAGE_CONTRACTS.md).

## Исполнение и остановка

Общего дедлайна задания сейчас нет: `generation_deadline_seconds=null`. Тайм-ауты отдельных внешних запросов и процессов остаются ограниченными. Один вызов LibreOffice по умолчанию ограничен 45 секундами. При явно заданном дедлайне supervisor использует `deadline_at`; позднее завершение не должно воскресить отменённое или завершённое задание.

Подготовка, предварительный анализ шаблона и генерация выполняются в отдельных worker-процессах; на POSIX управляется его группа вместе с дочерними процессами. Экспорты вариантов выполняются параллельно, операции PDFium сериализованы. Вторая активная генерация отклоняется атомарной резервацией SQLite. Полная поддержка нативного Windows не подтверждена; для Windows предусмотрен запуск через WSL2.

## Рендер и качество

PPTX сохраняет разрешённые исходные master/layout/theme и нативную графику. Старый текст удаляется, непроверенные фотографии и диаграммы не копируются как пользовательское содержание. При автоматическом выборе тесного макета допускается проверенная композиция из шрифтов и палитры шаблона. Явно выбранный pattern не подменяется таким способом; обложки и разделители сохраняют свои ограничения.

Таблицы измеряются по ширинам колонок и высотам отдельных строк, включая переносы заголовков. Аудит, PPTX, PDF и HTML используют общий расчёт. Значения не сокращаются ради вместимости.

Фактический PPTX повторно открывается и проверяется на данные, редактируемость и геометрию. LibreOffice создаёт PDF именно из PPTX; PNG получаются из PDF. Резервный PDF сцены при отсутствии LibreOffice явно отмечается и не подтверждает качество нативного экспорта. Лицензионные ограничения шрифтов могут потребовать растровый PDF/HTML — см. [FONTS.md](FONTS.md).

Отдельный visual critic проверяет изображения при `STUDIO_VLM_ENABLED=true` и разрешённой передаче данных. Неполная проверка не считается успешной. Ограниченный цикл изменения макета/читаемости проверяется повторным экспортом и аудитом. Полный upstream DeepPresenter visual reflection не подключён. Даже завершённая модельная проверка не заменяет ручную приёмку оформления.

При включённом VL подготовка также проверяет полноэкранные светлые растровые фоны: модель отмечает образцовое содержание, встроенное в пиксели, а ограниченный экстрактор очищает эти области до сборки фонового PPTX. Отдельная VL-проверка сложных отрисованных фонов отмечает занятые клетки для анализа текстовых зон; окончательные границы полей назначает код с проверкой геометрии и контраста. Оба пути используют настроенный `ModelGateway`.

`needs_review` означает доступные файлы с предупреждениями или незавершёнными дополнительными проверками. Ошибки финального аудита блокируют публикацию. Совпадение композиций отражается как ограничение разнообразия, а не маскируется статусом полного успеха.

## Данные, UI и диагностика

Подготовка: `accepted → running → ready | waiting_fonts | failed`. Генерация: `accepted → running → completed | needs_review | failed | timed_out | cancelled`.

Пакеты и исходный PPTX защищены контрольными суммами; перед генерацией проверяется целостность и версия. Изменение условий создаёт новый пакет. Старые результаты остаются в истории, но пакет несовместимой версии требует повторного анализа. Новые данные и SQLite по умолчанию находятся в `data/v2/`, вне Git; `STUDIO_DATA_DIR` переопределяет каталог. История из прежнего `data/` автоматически не мигрирует и не удаляется. Download API разрешает конечный список имён файлов и не отдаёт исходный PPTX или `package.json`.

В блоках «Дизайн-система» и генерации используются нейтральные сообщения об остановке. Технические причины сохраняются в журнале задания и диагностических файлах. `failure-report.json` и события анализа содержат `repair_issues` с кодом, действием, номером слайда и объекта. Секреты маскируются в журнале; файлы диагностики остаются локальными. Изменение формулировки сообщения не меняет адрес исправления.

## Провайдер и внешние компоненты

Текущая командная конфигурация: OpenRouter, `qwen/qwen3.8-27b`, Alibaba, без provider fallback и thinking. Сервер проверяет ответы независимо от JSON mode. Ключи не передаются в браузер и manifest. Правила работы с согласованной `.env.team` — в [CONTRIBUTING.md](CONTRIBUTING.md).

Vendored OpenDesign используется как набор инструкций дизайна; отдельного исполнения его daemon нет. DeepPresenter подключён через ограниченный адаптер; модель выбирает разрешённые операции и макеты. Лицензии и версии — в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). OCR имеет отдельный транспортный адаптер, но не включён в рабочий pipeline; генерация изображений не реализована.


## Тестовый контур

`tests/` проверяет контракты, безопасность, композицию и экспорт. `e2e/` запускает Chromium против настоящего изолированного HTTP-сервера: загрузка формы, анализ, генерация, скачивание, история, кэш и обработка отказов проходят через рабочие API и workers.

`test_support/replay.py` сопоставляет HTTP-запрос с фиксированным контрактом и возвращает заранее сохранённый синтетический ответ. Проверяются payload, хеш system prompt, схема и параметры генерации. Неожиданный запрос и неиспользованные ответы проваливают тест; сетевого fallback и автоматического обновления эталона нет. Production не импортирует этот модуль и не имеет режима выдачи тестовых ответов.

`test_support/app_server.py` задаёт отдельные настройки, временную папку и loopback-порт. Реальная `.env` и рабочие `data/` не используются. В модельном браузерном сценарии подменён только HTTP-провайдер; DeepPresenter, проверки и LibreOffice выполняются как обычно. Синтетические шаблоны создаются из параметров и seed, а не из пользовательских файлов.

GitHub CI содержит отдельные jobs линтера, Python-тестов и браузера. Диагностические артефакты браузера сохраняются при сбое. Это проверка поведения программы: фиксированные ответы критиков не доказывают качество актуальной модели. Политика сравнения изображений и правила изменения эталонов описаны в [TESTING.md](TESTING.md).


## Утверждение короткого брифа

По умолчанию `input_mode=content`. Режим `brief` запускается явно: исходные пользовательские материалы сохраняются в `original_content`, производные предложения — в `brief_evidence` с происхождением. `BriefDraft` содержит полный текст и заголовки конечного плана, а не краткую аннотацию.

`GET /api/packages/{pid}/draft` возвращает черновик и два хеша. `POST .../draft` создаёт новый пакет, отменяет таймер предыдущего и не наследует утверждение. `POST .../approve` атомарно сверяет `package_hash` и `draft_hash`. До утверждения ручная генерация и автозапуск запрещены. После утверждения пользователь выбирает один или три варианта и запускает генерацию вручную. Новые пакеты не создают таймер автозапуска; runtime поддерживает отмену таймеров старых пакетов. Смена режима провайдера не разрешает переписать утверждённый текст.

## Финальный аудит и выборочный ремонт

После автоматического ремонта и повторного аудита создаётся `final-audit.json` версии 1. Он содержит замечания, доступные операции и хеши файлов, к которым относятся выводы. Точный bbox показывается только при наличии проверенного индекса элемента сохранённой сцены.

`GET /api/generations/{gid}/findings` открывает этот снимок. `GET .../preview/{variant}/{slide}` выдаёт проверенное PNG. `POST .../repair` принимает `audit_hash` и `finding_ids`. Сервис проверяет снимок и допустимость действий; Store атомарно резервирует одно задание. Повтор того же запроса получает тот же ID.

Новая версия сохраняет `parent_generation_id`; исходная версия остаётся неизменной. Поддерживаются смена совместимого макета и улучшение читаемости диаграммы. Ошибка содержания требует отдельной правки и нового утверждения. Повторный аудит показывает устранённые, оставшиеся и новые замечания. Попытка ремонта сама по себе не доказывает исправление.

Только специальная ошибка `QualityGateRejected` делает заблокированный результат доступным как проверенный черновик. Обычная ошибка модели, сети или парсинга этого статуса не даёт. Обычные ссылки скачивания остаются закрытыми для всех failed jobs.

## Каталог ресурсов и выдача

Каталог извлекается из исходного PPTX до очистки. Типизированный ресурс связывает фигуру или группу с исходным слайдом, геометрией, изображением для предпросмотра, описанием и тегами. Исходник и превью проверяются по запечатанному пакету. Модельная классификация использует существующий gateway и кеш анализа шаблона.

Иконка размещается при смысловом совпадении и наличии свободного места. Режим скриншота `plain` остаётся стандартным; `device` использует отделимую рамку, сохраняя её нативные фигуры отдельно от изображения. Неоднозначные и слитые ресурсы не переносятся.

PPTX — основное действие результата. ZIP сохраняет выбранные один или три PPTX в корне; остальные форматы и отчёты находятся в подпапках. Автономный `evidence.html` содержит фактические проверки и ограничения конкретного запуска. Он не подменяет визуальную приёмку или реальные модельные прогоны. T2I в этом этапе отсутствует.
