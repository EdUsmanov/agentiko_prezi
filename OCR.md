# OCR: контракт и граница подключения

Источник: [официальная API-справка NeuralDeep](https://neuraldeep.ru/llms-full.txt), раздел «OCR · распознавание документов», проверено 23.09.2026.

## Что реализовано

`studio/ocr.py` — отдельный асинхронный адаптер, покрытый HTTP-контрактными тестами. Он **не включён в UI и конкурсный pipeline**. Реальный документ в OCR пока не отправлялся; квота страниц не расходовалась нашими тестами.

| Операция | API | Назначение |
|---|---|---|
| Загрузка | `POST /v1/ocr/extract`, multipart `file`, `model_profile` | Возвращает `id`, `page_count`, опционально `scan_pages_charged` |
| Состояние | `GET /v1/ocr/jobs/{id}` | Опрос не чаще раза в секунду, завершение `status=completed` |
| Результат | `GET /v1/ocr/jobs/{id}/result?format=markdown` | JSON с полем `content` |
| Остаток | `GET /v1/ocr/balance` | Документирован провайдером; адаптер пока не использует |

Авторизация: тот же Bearer-ключ, что для LLM. `fast` — стандартный профиль; `pro` по документации расходует две единицы квоты на страницу. Адаптер принимает PDF/PNG/JPEG. Сервис заявляет и другие форматы, но они пока не включены в наш клиент. Адреса preview в доступной справке не раскрыты — скачивание превью не реализовано.

## Место в архитектуре

OCR исходных сканов относится к **этапу подготовки без конкурсного дедлайна**, до `parse_content` и фиксации `PreparedPackage`. Для PPTX сначала применяется OOXML-парсинг: отправлять обычный PPTX в OCR не нужно. Анализ изображений на слайдах — отдельное расширение.

План подключения: загрузка → проверка файла/количества страниц → показ пользователю расхода квоты → однократный `submit` → сохранение ticket → `result` → карантин инструкций и извлечение фактов → привязка к исходным страницам → подготовленный пакет. Текущий транспорт возвращает Markdown; координатное происхождение по страницам и UI-подтверждение квоты ещё не реализованы.

OCR выходных презентаций, если он будет добавлен как проверка качества, относится уже ко **второму этапу** и обязан укладываться в общий лимит 300 секунд. Переносить такую проверку за таймер нельзя.

## Защита

- Endpoint и ключ задаёт сервер. Документ не может поменять адрес, профиль или авторизацию.
- Только HTTPS, redirects отключены. Job ID проверяется до построения URL; URL, `../`, query-параметры вместо ID запрещены.
- Нет автоматического повтора платного POST, в том числе при 429/5xx/таймауте. После неопределённого результата нельзя считать загрузку неуспешной и повторять её вслепую.
- Получение результата можно продолжить по сохранённому ID без новой загрузки.
- Ограничены размер входа и ответа, частота опроса и время ожидания. Ошибки провайдера не отражаются пользователю дословно.
- OCR-текст остаётся недоверенными данными: передавать его через `parse_content`, не в system prompt; не исполнять HTML, ссылки и команды из результата.
- Проверка magic bytes в адаптере — только проверка формата, **не** антивирус и не доказательство безопасности PDF. Перед публичным включением необходим отдельный изолированный загрузчик/валидатор.

## Что блокирует конкурсное включение

Провайдер называет движок SotaOCR, но доступная справка не устанавливает исходную модель, открытость весов, полный размер и лицензию. Условие «обработка в РФ» не доказывает соответствие требованиям хакатона. Нужны сведения о модели и разрешённость сервиса на соответствующем этапе. Для финала действует требование VK Inference; NeuralDeep не добавлялся в VK allowlist.

До этого адаптер остаётся заготовкой интеграции, а не заявленной работающей OCR-функцией продукта. Требуется также реальный тест на синтетическом одностраничном документе и проверка preview-контракта.
