# Соответствие второму хакатону и оценка адаптации

Дата: 24.09.2026. Оценка по текущему коду Forma после интеграции ограниченного DeepPresenter Design и аудита, а не по возможностям полного upstream PPTAgent. Источник новых требований — сообщение пользователя. Эти требования не внесены в действующий профиль VK: сейчас требуется оценка, не реализация второго продукта.

## Вывод

**Адаптация целесообразна: основу переписывать не нужно. Но это не замена поля ввода на загрузку Markdown.** Самые большие пробелы — полноценная структура документа, смысловой выбор визуализаций, новые типы редактируемых объектов и воспроизведение структуры шаблона. Текущий сервис не соответствует всем требованиям второго хакатона.

Условная сложность — средняя/высокая, около 6 из 10 для ограниченного конкурсного продукта. Это экспертная оценка трудоёмкости, не измеренная доля готовности. Для обещания качества на произвольных сложных шаблонах и разных офисных пакетах риск существенно выше.

## Матрица фактической готовности

| Требование | Сейчас | Что нужно |
|---|---|---|
| Загрузка `.md` и обязательного PPTX | PPTX загружается; Markdown вводится текстом, загрузки файла нет | Файл UTF-8, размер, ошибки кодировки, предпросмотр |
| Иерархия заголовков, вложенные списки, цитаты | Упрощённый построчный разбор; уровень `#` теряется, вложенность/цитаты не моделируются | Markdown AST и типизированный DocumentIR |
| Смысловые блоки, тезисы, сценарий | Факты, секции, таблицы, LLM-план, явный порядок «Слайд N» | Блочная семантика без потери иерархии, связей и оговорок |
| Автоматическое количество слайдов | По умолчанию 10 или заданный предел; не оценка сложности контента | Auto-планирование с проверкой вместимости и разрешённым диапазоном |
| Выбор типов и раскладок | Ограниченные роли и шаблонные зоны; Design выбирает pattern IDs | Типы cover/section/body/comparison/summary/closing и совместимость с визуализациями |
| Сохранение стиля шаблона | Палитра, основной точный шрифт, master/layout/theme, безопасный декор | Полнее учитывать смешанные начертания, сложные группы, текстовые логотипы и ограничения |
| Сохранение структуры шаблона | Геометрия/макеты сохраняются частично; титульный и финальный слайды не обязательны | TemplateGrammar: обязательные роли, допустимый порядок, соответствие роли макету |
| Текст и таблицы | Нативные редактируемые объекты; есть overflow/fit | Rich-text runs, настоящие уровни списков/цитат, разделение длинных таблиц |
| Столбчатые графики | Есть ограниченные горизонтальные бары из отдельных редактируемых фигур | Нативный Chart с редактируемыми данными, серии, оси, подписи и единицы |
| Линейные и круговые диаграммы | Нет | ChartSpec и отдельные renderers |
| Сравнения | Таблицы и колонки есть, отдельной смысловой модели сравнения нет | ComparisonSpec, согласованные критерии/единицы, таблицы или карточки |
| Процессные схемы | Есть заготовка линейной текстовой раскладки; политики вариантов её вытесняют | Узлы и связи, коннекторы, собственный layout и проверки |
| Таймлайны | Нет | Даты/интервалы/порядок событий, размещение и collision checks |
| Карточки показателей | Нет отдельного типа | Значение, единица, период, подпись, источник, style tokens |
| Изображения из Markdown | Ссылки не превращаются в картинки; сеть заблокирована | Контролируемый asset resolver, загрузка вложений, размеры, crop, происхождение |
| Генерация изображений при необходимости | Не реализована | Разрешённый T2I backend, политика выбора, стиль, лимиты, ошибки |
| Редактируемость | Текст/таблицы/фигуры — да; не весь спектр объектов | Структурные проверки каждого поддерживаемого типа, включая charts/connectors |
| Нет обрезаний/наложений | Детерминированные проверки и часть исправлений; `needs_review` возможен | Расширить audit/repair на новые объекты; плотные кейсы переразбивать на слайды |
| Р7-Офис на Astra Linux | Не проверено; сейчас LibreOffice в macOS | Испытания на согласованной версии Р7 и Astra, открытие/правка/сохранение |

Основания в коде: `studio/content.py` — parser; `models.py` — доступные сущности; `planner.py` — fixed count/variant policies; `native_template.py` — извлечение/перенос шаблона; `composer.py` — ограниченные композиции; `render.py` — native text/table и бары из фигур; `audit.py` — геометрия/покрытие; `deeppresenter.py` — выбор только разрешённых композиций. Полный DeepPresenter HTML/VLM runtime в эту оценку не засчитывается.

## Что оставляем

FastAPI, UI и историю; загрузку/валидацию PPTX; проверку и извлечение шрифтов; разбор masters/layouts; immutable package и hashes; ModelGateway; проверки происхождения данных; нативный PPTX renderer как основу; безопасный экспорт и состояние needs_review; ограниченный Design loop.

OpenDesign остаётся вспомогательным дизайн-контекстом. DeepPresenter полезен для оркестрации выбора/проверки, но подключение его полного upstream само по себе не добавляет в наш контракт Markdown hierarchy, ChartSpec, TimelineSpec или совместимость Р7.

## Предлагаемая архитектура адаптации

```text
.md → Markdown AST → DocumentIR → SemanticDeck
                                   ↓
                        Representation Planner → VisualSpec
                                   ↓
.pptx → TemplateCatalog + TemplateGrammar → Layout Matcher
                                   ↓
                       SceneIR → Native PPTX Renderer
                                   ↓
                 Audit / bounded repair / render comparison
                                   ↓
                       PPTX + отчёт проверок
```

### 1. DocumentIR вместо плоского списка фактов

Блоки: heading(level), paragraph, list(depth/order), quote, table, image_reference, visualization_hint. У каждого — source_id и диапазон строк. Связи родитель/ребёнок сохраняются. LLM получает эту структуру, не угадывает потерянную вложенность по плоскому тексту.

Разумный кандидат — markdown-it-py: он предоставляет токены и дерево, но семантические блоки и правила безопасности всё равно наши. Raw HTML отключить; текст и комментарии Markdown не получают прав менять инструменты или системные правила. [Документация parser](https://markdown-it-py.readthedocs.io/en/latest/using.html).

### 2. SemanticDeck и VisualSpec разделить

SemanticDeck описывает смысл, порядок, главный тезис, evidence и роль слайда. VisualSpec описывает выбранное представление: table, bar, line, pie, process, timeline, metrics или image.

Выбор — LLM с последующей проверкой данных, а не только regex. Даты могут обозначать независимые события (timeline) или ряд измерений (line). Доли должны иметь общий знаменатель; сумма процентов сама по себе не доказывает состав целого. Не смешивать единицы на одной оси, не выдумывать нулевые/пропущенные значения. При неоднозначности использовать таблицу либо запросить уточнение.

Нынешний assign_compositions нельзя оставить без изменения: он принудительно превращает почти всё в statement/columns/evidence/split/table/chart. Нужные timeline/process/line/pie должны переживать выбор варианта.

### 3. Сохранить структуру, а не старое содержание шаблона

TemplateGrammar хранит роли титульных/разделительных/информационных/итоговых слайдов, обязательные корпоративные блоки, допустимые зоны и совместимость макетов с VisualSpec. В отличие от нынешнего role penalty, структура становится проверяемым контрактом.

Нужно уточнить у организаторов, означает ли «структура шаблона» обязательный порядок/число секций либо наличие определённых типов и мастеров. Не следует копировать все демонстрационные слайды подряд. Если трактовка строгая, token-based composition нельзя использовать как безусловный fallback: потребуются только разрешённые макеты или явное сообщение о несовместимости.

### 4. Новые объекты и редактируемость

Для bar/line/pie — нативные PowerPoint charts с данными, осями и легендой. Для timeline/process/metric cards — редактируемые фигуры, текст и коннекторы, при необходимости группы. Нынешние бары из фигур редактируемы геометрически, но это не полноценная диаграмма с таблицей данных.

Используемый python-pptx уже имеет API создания столбчатых, линейных и круговых диаграмм; добавлять новую библиотеку ради базовых charts не обязательно. Но стилизация, выбор представления и совместимость остаются нашими задачами. [Официальная документация charts](https://python-pptx.readthedocs.io/en/latest/user/charts.html).

Обычная иллюстрация может быть отдельным изображением, которое пользователь заменяет/масштабирует/обрезает. Пиксели растровой фотографии не становятся редактируемыми векторными объектами. Это толкование «редактируемости всех поддерживаемых объектов» стоит подтвердить, а не обещать векторизацию любых картинок.

### 5. Изображения и безопасность

Не давать модели произвольный fetch. Предпочтительны загруженные вместе с Markdown изображения и проверенные asset IDs. Для внешних ссылок — отдельный resolver: разрешённые протоколы/домены, запрет private/loopback/link-local адресов и metadata endpoints, проверка DNS и каждого redirect, лимит размера/времени/пикселей, MIME sniffing и повторное кодирование. Подписи/OCR также недоверенные данные. Пользователь должен видеть факт сетевой загрузки.

T2I запускать только когда нужна иллюстрация и подходящего проверенного источника нет. Не генерировать графики с числами растровой моделью. Палитра и характер изображения выводятся из шаблона; учитывать лицензирование, бюджет и отказ провайдера. Ограничения моделей нового хакатона неизвестны — нельзя автоматически переносить туда VK-only или ≤35B, но существующую VK-политику нельзя отключать для текущего конкурса.

### 6. Проверка Р7 / Astra

LibreOffice здесь — полезный промежуточный renderer, но не доказательство совместимости с Р7. Нужна реальная доступная лицензированная установка согласованных версий. Проверять открытие без восстановления, шрифты/переносы, размеры и межстрочные интервалы, оси/легенды/данные диаграмм, редактирование таблиц и коннекторов, изображения, затем сохранение и повторное открытие.

Начать с небольшого compatibility deck из всех типов объектов, до сложного генератора. Результат фиксировать по каждому типу, а не одним флагом «работает в Р7». Прогон в целевом ПО желателен по предоставленному тексту, не объявляется новым жёстким требованием сдачи без уточнения.

## Раздельные конкурсные профили

Один репозиторий, общие IR/renderer/security, два профиля конфигурации. Не форкать весь продукт.

- VK: 3 варианта, общий дедлайн 300 секунд, действующая модельная политика, PPTX/HTML/PDF.
- Второй конкурс: Markdown upload, одна презентация по умолчанию, auto count, требуемый набор VisualSpec, template grammar, PPTX и совместимость целевого офиса.

В предоставленных требованиях второго конкурса нет обязательных 3 вариантов, 5 минут, HTML/PDF или конкретного лимита модели. Считаем это неизвестными/необязательными условиями до уточнения. Сейчас Plans и NAMES жёстко привязаны к трём вариантам: потребуется параметризация, а не простая галочка UI.

## Трудоёмкость для вашей команды

Оценка в человеко-днях разработчика, не в календарных днях; предполагаются переиспользование текущего кода, доступная модель, ограниченный набор поддерживаемых Markdown-конструкций и отсутствие сюрпризов с Р7/шрифтами. Команда: два разработчика, аналитик, тестировщик.

| Работы | Оценка |
|---|---:|
| Markdown upload, AST, DocumentIR, source mapping | 2–3 |
| SemanticDeck/VisualSpec, auto count, выбор представлений | 3–4 |
| TemplateGrammar и роли cover/section/summary/closing | 3–5 |
| Native bar/line/pie, process/timeline/metric cards | 5–7 |
| Проверенные изображения, T2I adapter и style constraints | 3–5 |
| Интеграция, новые audits/repair, исправления по Р7 | 4–6 |
| **Итого разработка** | **20–30** |

Дополнительно ориентир: 8–12 человеко-дней тестировщика и 3–5 аналитика. Эти работы частично идут параллельно разработке. Для двух разработчиков это 10–15 полностью загруженных рабочих дней; с интеграцией и зависимостью от целевой среды разумно планировать **3–4 календарные недели**. При хорошем раскладе ограниченный конкурсный вариант можно собрать за 2 недели, но это рискованный срок без большого резерва.

Ускоренный демонстрационный вариант на 7–10 рабочих дней возможен при 2–3 согласованных шаблонах, ограниченной вложенности Markdown, линейных процессах, таймлайнах с небольшим числом событий, 1–2 рядах данных и готовом T2I API. Это ограниченный scope, а не гарантия произвольного входа. Исключение T2I или timeline из демо не закрывает полный список требований: обязательность необходимо согласовать.

### Распределение

- Аналитик: семантические правила выбора VisualSpec, критерии неоднозначности, TemplateGrammar, примеры и критерии приёмки, вопросы организаторам.
- Разработчик A: Markdown/DocumentIR, semantic planner, auto count, новые контракты Design.
- Разработчик B: template grammar/matcher, native charts/shapes, layout/fit, assets/T2I.
- Тестировщик: эталонный набор Markdown × templates, цифры/источники/редактируемость, adversarial inputs, матрица Р7 и регрессии.

## Самый выгодный порядок

1. Уточнить структуру шаблона, объектную редактируемость, допустимые модели/сеть и версии Р7/Astra. Собрать compatibility deck.
2. Markdown AST → DocumentIR → SemanticDeck, не добавляя новых эффектов рендера.
3. VisualSpec и три нативных графика; затем process/timeline/cards. Вводить тип вместе с его audit и тестом.
4. TemplateGrammar и обязательные роли; автоматическое число слайдов с проверкой вместимости.
5. Assets/T2I и полный целевой прогон; финальный adversarial и совместимость.

**Рекомендация:** использовать Forma как основу. Главная новая инвестиция — промежуточная модель документа и визуализаций, а не ещё один агент или замена FastAPI. Это расширение пригодится и исходному VK-кейсу, но конкурсные политики должны оставаться раздельными.
